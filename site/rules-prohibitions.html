色

🔴 ブランド資産を改変しない

ロゴ・施設名の表記・ファビコンは、いかなる理由でも改変しない。 色を1つ変えることも、比率を変えることも、余白を詰めることも含む。

  • ロゴは施設の商標であり、名刺・看板・封筒など画面外の印刷物と揃っている。 画面の都合で変えれば、それらすべてと食い違う
  • 差し替えが必要な場合は依頼者から支給を受ける。こちらで生成・加工しない

⚠️ 色のトークンとロゴの色が食い違ったときは、トークン側で合わせる。 逆はしない。

🔵 --wine の明るさを勝手に変えない（承知のうえの例外）

--rose-500（--wine）は #FB4E76。白文字を載せると 3.25:1 で、 WCAG AA（4.5:1）を満たさない。

これは見落としではなく、依頼者の判断である。

  • 白文字を載せたまま 4.5:1 を満たす色のうち最も明るいのが #DB2E5E。 それより明るい選択肢は数学的に存在しない（＝「もう少し明るく」という調整はできない）

⚠️ 検査やレビューで再指摘されても、独断で暗くしないこと。 変えるなら依頼者に確認する。

該当するのは白文字を --wine の塗りに載せている2種類の部品だけ。 ピル型のボタン（.c-button--pill）と、右下の予約CTA（.c-floating__cta）。管理画面の主ボタン（共通の角型 .c-button）は画面を操作するボタンなので例外に入れず、--primary-solid（白文字 5.38:1）を使う。

例外を広げないための線引き

使う色理由
ブランドの見せ場（ボタン・CTA）--wineブランドカラーを優先。不合格を承知で維持
本文へスキップ--wine-deep支援技術のための機能（白文字 4.15:1。ユーザーの決定で他の --wine-deep とそろえた）
FAQの通し番号 Q1--wine-deep読ませるための文字であって、ブランドの見せ場ではない
小さいピンク文字・現在地・ホバー--wine-deep文字なので --wine より濃い色を使う（4.15:1）

--wine-deep（--rose-550 = #E23C63）は白の上で 4.15:1。4.5:1 に届かないことを承知のうえでの決定。これより明るくしない。変えるなら依頼者に確認する。

🔴 CSSに色を直書きしない

CSS

コードを表示コピーしました
/* ✗ */  color: #FB4E76;
/* ✗ */  background: rgba(255, 249, 248, .9);
/* ✓ */  color: var(--wine);
/* ✓ */  background: rgba(var(--bg-rgb), .9);

check_colors.py が止める。半透明が必要なら -rgb 版のトークンを使う。

🔴 プリミティブを直接参照しない

CSS

コードを表示コピーしました
/* ✗ */  color: var(--rose-500);
/* ✓ */  color: var(--wine);

プリミティブ（--rose-500 など。色ごとに20段）はセマンティック層を定義するためだけにある。 役割で名前が付いた層（--wine --ink --line …）だけをCSSから使う。

🟠 料金以外を --bg-soft で塗らない

塗りが付いていたら料金がある、と全ページで読めるように揃えてある。

使ってよいc-price / c-card--priced
例外c-table__head（表のヘッダー帯）だけ。これを前例に広げない

🟠 小さい文字のピンクに --wine を使わない

--wine-deep を使う。--wine（3.25:1）より読みやすいため。

🟠 「当施設で対応していない」カードの面を塗らない

バッジの文字が意味を伝えるので、地の色まで変えなくてよい（グレーの濃さを4段階試したうえでの結論）。 どうしても塗るなら #F4F1F1 より暗くしない — カード内の「※」注記（--ink-soft 13px）が コントラスト比 4.5:1 を割る。

余白

🔴 4の倍数以外を使わない

4 / 8 / 12 / 16 / 20 / 24 / 28 / 32 / 36 / 40 / 44 / 48 / 52 / 56 / 64 / 68 / 72 / 84 / 88

check_rules.py が padding / margin / gap を検査する（4 の倍数か）。新しい段を増やさない。 表にない値が要ると思ったら、まず既存の段で代用できないか検討する。

🟠 文字サイズの段を増やさない

公開サイトは 28 / 24 / 20 / 18 / 16 / 14 / 12px の7段＋clamp() 3つ。 管理画面は 24 / 18 / 16 / 14 / 12px の5段。これ以外の値を書かない。

  • rem を使わない。 公開サイトも管理画面も px 系でそろえている
  • 0.5px刻み（16.5 / 15.5 / 14.5 / 13.5 / 12.5 / 10.5）は復活させない。並べても見分けが つかない一方、「どれを使うか」の判断を毎回発生させていた
  • 例外はスマートフォンの営業時間表だけ。横スクロールさせずに収めるため 12px に落としている
  • 見出しにサイズを書き忘れない。ブラウザ既定の倍率（2em / 1.5em / 1.17em）に任せると 30 / 22.5 / 17.6px という半端な値になる（管理画面で実際に起きていた）

🟠 ボタンやバッジのラベルを折り返させない

幅が足りないときに詰めるのは、ボタンではなく他の列。

日本語のラベルは2文字が多く、少し幅が足りないだけで「編 / 集」「公開 / 中」と 1文字ずつ縦に割れる。押せるものが縦書きになっていると、壊れて見えるうえに押しにくい。

CSS

コードを表示コピーしました
/* ✓ ラベルは折り返さない */
.c-button, .a-status { white-space: nowrap; }

/* ✓ 一覧表は1列目（可変）＋残りは内容ぶんの幅 */
.c-data-table th + th, .c-data-table td + td { width: 1%; white-space: nowrap; }
  • 表ではいちばん長くて折り返してよい列（タイトルなど）に余りを吸わせる
  • それでも収まらない幅では、.c-data-table の overflow-x: auto で横スクロールさせる。 ボタンを縮めない
  • ⚠️ <button> には font: inherit を付ける。 無いとブラウザ既定の 13.3px になり、 同じ行の <a class="c-button">（16px）と大きさが食い違う

⚠️ 管理画面の記事一覧で実際に起きていた。<td> 自体を flex にしていたため 表のセルとして幅を計算できず、操作列が先に潰れていた。flex は <td> の内側の要素に持たせる。

🟠 余白はトークンで書く

内側は --p-*、外側は --m-*、並びの間は --gap-*。px を直接書かない（書くなら4の倍数。check_rules.py が調べる）。

命名

🔴 接頭辞なしのクラスを作らない

c- 共通 ／ p- ページ固有 ／ l- レイアウト ／ u- ユーティリティ ／ a- 管理画面 ／ is- has- 状態。

🔴 BEMを2段以上に深くしない

c-card__head__title は作らない。要素（__）は1段、派生（--）は1つまで。

🔴 状態クラスを単独で定義しない

CSS

コードを表示コピーしました
/* ✗ */  .is-active { … }
/* ✓ */  .c-faq__item.is-active { … }

管理画面と公開サイトで .is-active が衝突していた実例がある。

🔴 旧クラス名を出力に残さない

check_rules.py がHTML の class 属性を CSS に実在するクラスと突き合わせる。

したがって、ソースの目視でも class 属性の一括置換でも漏れる。 検査は必ず出力されたHTMLに対して行う。

🟠 p- を他のページで使い回さない

使い回したくなったら、それは c-（共通コンポーネント）に昇格させるべきもの。

🟠 ID をクラスと同じ扱いにしない

site-header mobile-nav nav-toggle floating-top は旧名のまま。 JSが getElementById で参照し、aria-controls からも指されている。 一括置換で書き換えて、ヘッダー固定・モバイルナビ・トップへ戻るが同時に壊れたことがある。

🟠 1語のクラス名をコード全体で置換しない

note alt yes no lead in open は、JSONのキーやブロック型名としても同じ綴りで存在する。 単語境界だけで置換すると "note": "…" というJSONのキーまで書き換わり、データ構造が壊れる。 実際に build_patterns.py のデータ定義を破壊して全面やり直しになった。 置換するなら class="…" の中だけに限定する。

フォーム

🟠 入力欄のラベルをプレースホルダーで代替しない（例外あり）

原則NG。 プレースホルダーは入力を始めると消えるため、 「何を入れる欄だったか」を確かめられなくなる。読み上げソフトの扱いもブラウザ差がある。

例外として許容するのは、次の2つを両方満たすときだけ。

  1. ラベルが無いほうが画面としてすっきりする（行の中に置く入力欄など、 ラベルの1行が入ると行が縦に伸びてしまう場合）
  2. ラベルが無くても何を入れる欄か想像がつく（周囲の見出しや文脈で自明）

許容する場合も、aria-label を必ず付ける（読み上げ用のラベルは残す）。 placeholder だけにして aria-label を省くのは、例外の範囲外＝禁止。

例判断
よくある質問グループ管理の「グループ名」「新しいグループ名」許容
記事編集のタイトル・公開日時ラベルを置く（必須項目で、入力後も確かめたい）
接続設定のプロパティURLラベルを置く（形式の説明が要る）

JavaScript

🔴 JSが付けるクラスとCSSが待つクラスをズラさない

check_rules.py の最重要の検査。HTMLの構造比較では検出できない（JS実行後にしか差が出ない）。

⚠️ CSSだけ is-in に改名して JS が in のまま残り、u-reveal が永久に opacity: 0 となって トップページがヘッダー以外すべて消えた。

🟠 JS前提のUIをHTMLに書かない

目次の送りボタン（c-toc__more）はJSが生成する。JSでしか動かない操作のため、 HTMLに置くとJS無効時に押せないボタンが残る。

🟠 <details> の開閉をJSで実装しない

よくある質問・交通アクセスは <details> / <summary>。JS無効でも開ける状態を保つ。

ビルド・運用

🔴 公開ディレクトリに「配信しないファイル」を置かない

公開ディレクトリに置いたものはすべて配信される。 一覧ページの既定が別のファイルになっていても、旧ファイルを直接叩けば200で返る。

見本・移行の入力データ・確認用ページは、配信されない場所に置く。

置き場所を分けたら、実際にURLを開いて配信されないことを確かめる。

🔴 検査の除外リストで問題を「見なかったこと」にしない

検査を黙らせるために除外リストへ足さない。直すか、そもそも配信しない場所へ移す。

除外リストに足したくなったら、そのファイルがそもそも正しい場所にあるかを先に疑う。

🔴 ID もクラスと同じく「JSが探しているもの」として扱う

site-header mobile-nav nav-toggle floating-top は改名しない。

check_rules.py が、js/site.js を読むページに、JS が getElementById で探す ID があるかを突き合わせる。

🟠 生成されたHTMLを直接編集しない

一覧ページ・記事ページ・サービス案内は自動生成物。次の生成で消える。 修正は必ずデータ側かテンプレートに入れて、生成をやり直す。

🟠 CSS/JSを変えたら ?v= を変える

変えないと、利用者のブラウザが古いCSSを読み続ける。まとめサイトと練習課題は build.py が付け直す。 算出方式を複数箇所で持たない（食い違うとページによって別のURLでCSSを読む）。

🟠 CSSを変えたら、生成物も作り直す

コマンド

コードを表示コピーしました
python3 scripts/build.py          # トークン・まとめサイト・AI 向け資料を作り直し、最後に検査が走る

生成物（tokens/tokens.css・site/*.html・DESIGN.md・docs/）を手で編集しない（正本から作り直す）。

🔴 検査を回避してコミットしない

色・決まりの検査で違反が出たまま公開しない。 どうしても通したい事情があるときは、回避せず理由を報告してからにする。

設計方針

🟠 Tailwind を導入しない

ビルドせずそのままアップロードする方針のため。 ただし Tailwind の構成は採り入れている（プリミティブの数値スケール → セマンティック、検査による制約）。

🟠 ユーティリティクラスを増やさない

u- は u-nowrap / u-num / u-reveal / u-br-sp / u-visually-hidden の5つだけ。余白・色のユーティリティは作らない。 増やすとコンポーネントの外側で見た目を上書きでき、規約の意味がなくなる。

🟠 未使用のCSSを残さない

🟠 同じ役割のコンポーネントを増やさない

統合の実績 — ブロック見出し3種 → c-block-title（27箇所）／ 白い囲み3種 → 共通ルール ／ 表2種 → c-table ／ 箇条書き3種 → c-list。 新しい見た目が必要になったら、まず既存のどれかで足りないかを確認する。

文章（サービス案内のみ）

⚠️ ルールが及ぶのは サービス案内のデータ だけ。

🟠 よくある質問・お知らせ・コラムの表記を揃えない

お知らせ・コラムはWP REST APIから取り直すため、手で直しても次のビルドで戻る。

🟠 使わない表記

使う使わない
ください／いただく／ため／など／とくに／および下さい／頂く／為／等／特に／及び
、。半角の ,. !? ／三点リーダ ／半角括弧
〜（U+301C）ハイフンやチルダでの範囲表現
〜とされています〜と聞きます ／ 〜ようです
いるおられる
  • 口語の副詞（いろいろ／かなり／やはり）と「分かりやすく言えば」を使わない
  • 箇条書きに句点を付けない。 段落には付ける
  • 見出しを話し言葉にしない（「どのくらい効果があるの？」→「効果の目安」）

例外: 「こんなときにご相談ください」「こんなお悩みはありませんか？」は残す。

🔵 専門的な内容を足さない

サービス案内12ページは公式サイトの記載を利用者視点に再構成した要約・言い換え。 新規の専門的な情報は足していない。公開前に代表者の内容確認が必要。

根拠のない数字を書かない（出典または算出根拠を必ず添える）。
